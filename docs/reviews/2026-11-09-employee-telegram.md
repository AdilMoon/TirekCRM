# Telegram: адверсариальное ревью

## Область

TelegramPairing/Link/Delivery/BotState/UpdateReceipt и SQL-миграция, исходящий транспорт, self-service привязка, обработка getUpdates, очередь назначений, запись фото в паспорт с дополнительным контекстом привязки/задачи, RU/KK/EN и формы сотрудника/владельца. Приватный backup сделан до миграции; токен пользователя находится только в .env. Бот @tirekcrmbot проверен через реальный getMe, существующего webhook при проверке не было.

После итоговых проверок запущен обычный dev:https с настройками Gmail/Telegram из .env. Повторно подтверждены реальный getMe, успешный getUpdates по свежему lastPollAt (UTC), HTTPS health и главная страница — 200. Перезапуск во время первичной компиляции потребовал дождаться восстановления lease, защиту от второго poller не отключали.

## Перечитывание с попыткой нарушить границы

- Identity из браузера не принимается: строгие locale/pairingId без userId/chatId/organizationId. Связь создаётся для текущего активного EMPLOYEE, с неизрасходованной 10-минутной ссылкой и отдельным подтверждением в CRM. До подтверждения /start лишь предъявляет профиль. Ссылка хранится как SHA-256, перевыпуск меняет токен/ID, второй claimant не заменяет первого; один Telegram ID не захватывает уже привязанный аккаунт.
- Telegram updates принимаются только исходящим клиентом фиксированного api.telegram.org по TLS. Публичного webhook-интерфейса с поддельным JSON нет. У сообщений проверены private chat, реальный числовой sender ID, соответствие chat ID, is_bot; группы и несоответствие отправителя/чата не получают данные. Умеренный лимит сообщений на отправителя ограничивает автоматические ответы. Callback_data содержит лишь действие/UUID, право на задачу проверяется заново.
- Карточка и список ограничены своими активными задачами. Проверены чужой сотрудник/компания, неподходящая роль, деактивация. Перед записью фото проверены конкретная активная задача, заказ, текущий UUID привязки и актуальный выбор. Смоделированы переназначение, отключение пользователя и отвязка именно во время скачивания: новая фотография не появилась. Старый снимок до выбора/новой привязки и истёкший выбор также не сохраняются.
- Фотография всегда AFTER/shared=false. Идемпотентный UUID зависит от bot ID, private sender и Telegram message_id; повтор update/message даёт одну строку фото и один аудит. EXIF удалён; исходный тестовый PNG доказанно содержит EXIF, сохранённый JPEG — нет. Фото не появилось в публичном паспорте. Подмена внутреннего Telegram-контекста через публичный photo API даёт 400. Прежние границы 6 фото/размеров/пикселей не отключались.
- Файлы скачиваются только с фиксированного HTTPS-адреса Telegram; редиректы запрещены, path traversal/неожиданные пути отклоняются, размер ограничивается и метаданными, и фактически прочитанными байтами. SVG/анимация/декодирование сверх 12 млн пикселей не допускаются. Строки задачи идут без parse_mode, управляющие/одиночные суррогаты очищаются, границы UTF-16 при обрезке не ломают emoji. UI показывает профиль как текст, включая строку с угловыми скобками.
- Очередь назначений создаётся вместе с исходным notification, FK связывают её с организацией, получателем и привязкой; duplicate-safe ключ не дублирует очередь. Worker строит карточку заново, пропускает неактуальную задачу, учитывает 429/retry_after. 403 удаляет привязку; /stop работает и после деактивации сотрудника. Новые временные поля очереди/привязки/receipt задаются явным new Date(): это исключает задержку из-за локального PostgreSQL TimeZone=Europe/Moscow при TIMESTAMP defaults.
- Lease по bot ID не даёт двум экземплярам одной БД опрашивать одновременно. Offset и receipts сохраняются после обработки; дубликаты и постоянный provider 400 проверены. Проверка прямой повторной обработки фото дополнительно доказывает идемпотентность вне receipt. Внешний sendMessage и commit БД не атомарны: повтор текста при неопределённом ответе остаётся возможным и описан в инструкции. Lease не координирует другой проект/другую БД с тем же токеном.
- Provider exceptions заменены безопасными кодами без URL/токена; логи содержат только фиксированные маркеры. Статус API не отдаёт tokenHash, raw token, числовой Telegram ID или данные коллег. Аудит подключения/отключения без копий токенов/сообщений. Успешная доставка не возвращает доступ после переназначения; уже доставленные сообщения/копии невозможно отозвать.

## Проверки и ограничения

Обязательные check:structure, typecheck, npm test, build пройдены; backend unit — 28, локализация — 3. Интеграции Telegram/распределения/команды/паспортов — 35 тестов Node runner, включая 4 родительских теста, на собственных организациях с fake Telegram transport и реальным PostgreSQL. Microsoft Edge: 12 сценариев Telegram, workspace/onboarding и фото-паспорта прошли в отдельных прогонах. Проверены явное согласие, профиль, подключение/отключение, 390 px и RU/KK/EN; provider boundary в новом UI-тесте моделируется, не выдаётся за живой Telegram E2E. Снимок мобильной формы просмотрен. Прогоны на dev API прерывались watch-перезапуском и Fast Refresh при компиляции нового маршрута; итоговый браузерный набор выполнен на собранном варианте без watch. Быстрый набор израсходовал действующие 10 входов/минуту: подтверждён HTTP 429/Retry-After, оставшиеся сценарии прошли после обновления окна. Защитные лимиты не менялись. Сравнение со старым пользовательским снимком выявило новые изменения заказа/документа/паспорта/сеансов в существующей компании; тесты изменяли только собственные UUID, чужие изменения не откатывались.

Текущий срез не меняет статус задач из бота, не принимает документы/произвольные файлы и не публикует снимки клиенту. Часы дороги и расписания остаются прежней функцией CRM. Вход/подтверждение привязки localhost выполняются на этом компьютере; сам бот работает с телефона при работающем сервере. Период простоя, превышающий хранение updates у Telegram, не восстанавливает сообщения: активные задачи остаются в CRM и /tasks. Отвязка прекращает последующие действия, но не удаляет доставленные сообщения. Доставка не гарантирует прочтение, уникальность внешнего текста или подлинность содержимого фотографии. Сквозной живой тест физического аккаунта сотрудника требует его участия; реальный бот отдельно проверяется на getMe и успешный polling. Успешные тесты не являются гарантией безопасности или готовности к публичному запуску. Перед коммитом проверяются локальные секреты и состав файлов; результаты, изображения, БД и .env исключены.
