# Контроль оплат по заказам

Владелец открывает **Финансы → Контроль оплат**. Нового раздела в боковом меню нет. Отсюда можно найти заказ по номеру, названию или клиенту, отфильтровать срок, открыть последний действующий черновик счёта или карточку заказа и записать уже полученную оплату обычным способом. Сохранение оплаты обновляет список; полностью оплаченный заказ исчезает. Кнопка «Обновить» получает изменения из других сеансов.

## Расчёт

- Одна строка на заказ. Остаток = текущая стоимость заказа − платежи + возвраты платежей. Расходы, сметы и суммы нескольких счетов не складываются с этим остатком.
- Только положительные остатки, исключая отменённые заказы. Бесплатные повторные выезды не создают задолженность.
- Срок оплаты берётся из последнего `INVOICE_DRAFT` по `createdAt DESC, number DESC, id DESC`. Акты не меняют срок. Если последний счёт аннулирован или без даты, предыдущий срок не восстанавливается. Дата выполнения заказа не является сроком оплаты.
- Срок прошёл, если дата строго раньше сегодняшней даты в `Asia/Almaty`. Сегодня относится к «Срок не прошёл». Без счёта/срока заказ попадает в «Без срока оплаты».
- Приоритет: прошедшие сроки, затем текущие/будущие, затем без срока; внутри — дата и номер заказа. По умолчанию 20 строк. Итоги включают все строки с выбранными фильтрами, а не только текущую страницу.
- PostgreSQL считает деньги в `numeric`, API передаёт десятичные строки. Клиент форматирует их без потери копеек через `BigInt`.

## API и ограничения

`GET /api/payments/control?q=&page=1&pageSize=20&state=OVERDUE`

`state`: `OVERDUE`, `SCHEDULED`, `NO_DUE` или отсутствует. Общие ограничения поиска и страниц, строгая схема без произвольных полей и фильтра организации. Только активный владелец с действующей сессией; сотрудник получает 403. Ответы `no-store`, лимит 60 запросов/минуту на маршрут дополнительно к общим ограничениям.

Одно SQL-выражение с одним снимком MVCC одновременно вычисляет строки, остатки, статусы и итоги. Возвраты сначала агрегируются по платежу, платежи — по заказу: несколько дочерних записей не умножают деньги. Все чтения ограничены организацией из сессии.

Это внутренний контроль по текущим заказам и срокам черновиков, а не юридическое подтверждение задолженности, сверка с банком или распределение платежей по отдельным счетам. Письма клиентам не отправляются автоматически. При изменении стоимости заказа показывается текущий остаток; сохранённый счёт остаётся неизменным. Смена фильтра/даты в другом сеансе появляется после обновления, автоматического фонового опроса нет.

## Проверки

```powershell
node --env-file=.local/attention-qa.env --test tests/payment-control.integration.mjs
$env:PLAYWRIGHT_CHANNEL='msedge'
node --env-file=.local/attention-qa.env node_modules/@playwright/test/cli.js test tests/browser/payment-control.spec.ts
```

Проверки используют отдельную локальную QA-базу и созданные ими организации. Переменные подключения и данные сессий не включаются в репозиторий. Перед браузерными проверками должны работать QA API и веб-приложение на портах 4000 и 3000.
