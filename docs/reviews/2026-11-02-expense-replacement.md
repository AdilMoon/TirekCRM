# Адверсариальное ревью: атомарная замена расхода — 2026-11-02

## Область

Новый POST /finance/expenses/:id/replacement, полный контракт целевого расхода,
связь нового расхода со сторно в БД и дополнительные ссылки в GET карточки.
Изменения отдельно перечитаны с проверкой ролей/организаций, ключей повторов,
конкуренции, точности денег, дат, ошибок и обратной совместимости.

## Конкретные результаты

- OWNER и его организация определяются SessionGuard; активный владелец повторно
  проверяется в транзакции. Отсутствующий сеанс — 401, EMPLOYEE — 403, чужой расход
  или заказ — 404, недопустимый/отсутствующий Origin — 403. Заблокированный владелец
  отвергнут и через HTTP, и прямым вызовом сервиса. Данных других компаний в ответах нет.
- Контракт строгий: сумма положительная и точная, описание/причина ограничены,
  некорректный Unicode/NUL запрещён; неизвестные поля организации/автора/даты/нового
  идентификатора отклонены. orderId обязателен как UUID или null: пропуск не может
  незаметно отвязать расход от заказа. Полная замена без фактического изменения — 409.
- Три параллельных одинаковых запроса вернули один и тот же 201: один новый расход,
  одно сторно и два события аудита. Другой ввод/автор/источник с прежним ключом — 409
  без записей. UUID нормализуются; исходный расход сравнен целиком и не изменился.
- Отдельно проверено смешение старого и нового маршрутов с одним ключом. Старый
  reverse теперь явно отвергает ключ сторно, содержащего replacementExpenseId;
  replace отвергает ключ standalone-сторно. Оба направления дают 409. Обычные
  повторы legacy-сторно сохраняют прежнее поведение, подтверждённое регрессиями.
- Разные ключи замены одного расхода: ровно один 201 и один 409. Замена против
  простого сторно с общим и разными ключами: также один победитель, без лишнего
  расхода или частичной замены. Существующий Serializable helper повторяет целую
  транзакцию при конфликте; ограничения не отключались для прохождения тестов.
- Чтение во время незавершённой транзакции проверено с управляемой паузой перед
  первым аудитом, когда оба финансовых INSERT уже выполнены. Другой запрос видит
  исходный расход и сумму 10.10; после commit — три движения и сумму 12.34.
  Промежуточный расход или одно сторно наружу не видны.
- Ошибка второго события аудита откатила новый расход, сторно, ссылку и первое
  событие аудита. После сбоя тот же ключ успешно повторён. Проверено отсутствие
  дополнительных событий при успешных повторах; причина и описание не дублируются
  в метаданных аудита. Используются прежние локализованные коды событий.
- Цепочка A → B → C сохраняет обе ссылки у B. Повтор A → B после B → C возвращает
  прежний сохранённый результат, а не текущее состояние другой операции.
- Исходные суммы NUMERIC(18,2) не проходят через Number: исторические 90071992547409.99
  сторнированы полностью, новый расход 0.01 дал точный чистый расход 0.01 в отчёте
  и CSV. Проверены обзор, общие итоги и неизменность исторического дня.
- У нового расхода и сторно одинаковый createdAt; ввод даты пользователем запрещён.
  Современные корректировки не переписывают периоды исходных операций. Изменение
  привязки заказа не меняет стоимость, оплаченный остаток или версию заказа.
- Миграция добавляет nullable-поле без UPDATE/DELETE исторических данных.
  PostgreSQL отверг ссылки на чужую организацию, на самого себя, повторную цель
  замены и удаление нового расхода с существующей ссылкой. Старые standalone-сторно
  с null продолжают создаваться и повторяться.
- В рабочем https://localhost:8443 POST вернул 201, повтор вернул тот же результат,
  итог 0.11 точен; системная проверка CA не отключалась, Cache-Control: no-store сохранён.
  Эта проверка создала и удалила только свою организацию.

После финального перечитывания дополнительных воспроизводимых дефектов в затронутой
области не найдено. Все тестовые изменения ограничены созданными ими организациями;
рабочая демо-организация не редактировалась. Изолированные API тестов остановлены.

## Ограничения

Изменён API; формы атомарной замены и переходов по цепочке в UI пока нет. Старые формы
сторно/добавления расхода работают отдельно. Браузерная регрессия UI не проводилась:
его код не менялся; проверены совместимые старые API и HTTP/HTTPS нового маршрута.
Политика денег/дат и ограничения суммы новых расходов остаются прежними. API не
реализует возврат поставщика, бухгалтерскую проводку, отмену финансовой истории или
банковское движение. После потерянного ответа клиент обязан сохранить ключ и тело.

Произвольные действия администратора БД не защищаются бизнес-логикой. Уникальные
ссылки и запрет самоссылки не являются общим SQL-запретом циклов произвольной длины;
API исключает их созданием только новой целевой записи. Массовые удаления для
администрирования должны учитывать новые FK. Восстановление БД, нагрузочные сценарии
и внешний аудит не проводились. Успешные проверки не гарантируют безопасность всего
приложения и готовность к коммерческому запуску.

Основание транзакционного подхода: [PostgreSQL — Serialization Failure Handling](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html).
