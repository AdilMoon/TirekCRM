# Адверсариальное ревью: исправление расходов в интерфейсе

Дата: 25 ноября 2026. Повторно прочитаны изменения формы, выбор заказа, расширенные DTO, финансовый сервис и интеграция с отчётом. Проводки и транзакционный алгоритм замены остаются в существующем FinanceService.

## Найденные дефекты и решения

1. **Скрытая потеря выбора заказа при смене режима.** В первой реализации ID находился в родителе, а подпись выбранного заказа — в размонтируемом picker. После «Только сторно → Исправить расход» отсутствующий на первой странице выбранный заказ отображался как пустой, хотя отправлялся его ID. Воспроизведено в Edge на заказе вне первых 20 записей: `select.value === ''`. Исправление: весь краткий выбранный заказ хранится в форме, picker управляемый, выбранный вариант всегда добавляется в список. Повторный тест проверяет выбор до и после переключения, запись, прибыльность и явное снятие связи.
2. **Исправление без изменения блокировало бы форму после 409.** Предзаполненная форма и одна новая причина не меняют реквизиты. Добавлена проверка нормализованных строк суммы, описания, категории и заказа до создания pending-запроса. При отсутствии изменений форма остаётся редактируемой и не создаёт сторно. Серверная проверка сохранена. При добавлении проверки сборка поймала некорректное сужение типа результата нескольких Zod-схем; результат схемы замены теперь хранится отдельно, повторная типизация и production-сборка проходят.
3. **Разные URL при повторе могли бы изменить смысл операции.** Pending хранит URL вместе с неизменным сериализованным телом. После потери ответа поля, режим и переходы к другим операциям блокируются до успешного повтора либо закрытия. Edge воспроизводит серверный успех с потерянным ответом, затем 429 и повтор: создаются ровно одна замена и одно сторно, тела трёх запросов одинаковы.
4. **Длина причины расходилась с контрактом.** HTML maxLength приведён с 1000 к 500 символам. Проверка схемы остаётся перед отправкой и на сервере.

## Проверенные границы

- Новые поля ответа возвращаются только для операции своей организации; порядок загрузки не разрешает обход SessionGuard. Интеграционные проверки покрывают 401, 403, чужие операции/заказы 404, Origin и запрет подмены организации, автора и дат.
- Краткий заказ берётся из составной связи БД внутри ограниченной организацией операции. Кнопки перехода открывают существующие защищённые карточки. HTML в описании отображается текстом, без элементов img/script.
- `replacementAllowed` не разрешает запись сам по себе. Складская закупка скрывает замену в интерфейсе; сервер отдельно запрещает её. Параллельное сторно после открытия формы даёт 409, новая запись не создаётся. Отзыв доступа очищает открытую финансовую карточку существующим обработчиком.
- При выборе другого заказа исходная связь не теряется молча. Тест на 26 заказах, включая два вне первой страницы, проверяет переход затрат `10.11 → 12.34`, перенос `7.07` с исходного заказа на другой и последующее явное снятие связи. Проверяется `actual.expenses` реального API прибыльности.
- Расчёты сервера остаются в bigint/Decimal. UI передаёт строки, нормализует запятую; проверка отсутствия изменения дополняет дробь строкой без Number. Исходная дата/сумма сохраняются, новая операция отражается текущим периодом. CSV и отрицательные месяцы проверены существующими сценариями.
- Интеграционные проверки конкурентных ключей, замены против сторно, отката при ошибке аудита, неизменности исходной записи и точности больших сумм пройдены. Исправление атомарно через существующий Serializable API.
- Мобильная форма проверена в Edge на ширине 390 px на RU/KK/EN, с длинным описанием, недоступным поиском и сохранением выбранного заказа. Ошибка поиска не снимает связь; повтор восстанавливает загрузку. Изменение языка выполняется обычным переключателем между открытиями модального окна.

## Результаты проверок

- Microsoft Edge: 10/10 сценариев — новая форма (4), существующие возвраты/сторно/CSV (4), контроль оплат (2). Финальный прогон выполнен после исправления выбора и проверки отсутствия изменений. Мобильный PNG просмотрен.
- PostgreSQL-интеграция: 22/22 проверки в expense-replacement.integration.mjs и finance-adjustments.integration.mjs; расширены проверки краткого заказа и доступности замены.
- `npm test`: 29 backend + 3 localization; `check:structure`: 1172 записи переводов и границы модулей. `git diff --check` без ошибок, `npm audit --omit=dev --audit-level=low`: 0 известных уязвимостей на момент проверки.
- Native и Docker production-сборки прошли после исправления типизации. HTTPS health 200, финансовая карточка без сессии 401, внешний маршрут внутренних метрик 404. Контрольные хеши рабочих заказов, клиентов, организаций и задач, количество пользователей/фото и суммы оплат/расходов до и после обновления совпали. Проверки меняли только созданные ими организации в отдельной QA-базе.

## Оставшиеся ограничения

Pending хранится в памяти окна, а не после перезагрузки браузера. Перед новой попыткой после закрытия окна с неизвестным результатом нужно проверить историю; интерфейс сообщает об этом. Складские закупки не заменяются этим сценарием. Банковские переводы, автоматическая сверка и юридическая оценка исправлений не добавлены. Проверки не являются гарантией безопасности или готовности к рынку.
