# Объяснимое распределение сотрудников: адверсариальное ревью

## Перечитанная область

Новые WorkProfile/WorkBooking и две SQL-миграции, строгие контракты, planner/SchedulingService, связи с переходами заказа и редактированием/статусами задач, профили команды, подбор в карточке заказа, аудит, RU/KK/EN. Telegram не реализуется в этой итерации. Перед миграциями сохранён приватный native backup; секретные настройки не менялись.

## Найденные проблемы и исправления

- DEF-SCHED-TIME: прямой SQL INSERT пересекающегося интервала неожиданно проходил, хотя API считал сотрудника занятым. На установленном PostgreSQL TimeZone=Europe/Moscow. Текущий Prisma pg adapter передаёт DateTime без смещения, а его нормализатор timestamptz заменяет смещение на UTC; отсюда расходились физический момент и время, возвращаемое приложению. Новые интервалы переведены на UTC TIMESTAMP(3) и tsrange, по принятому в проекте способу хранения DateTime. Добавлена отдельная forward-миграция: уже применённая первая миграция не переписывалась. Таблица ещё содержала только собственные тестовые данные, удалённые cleanup. После исправления прямой SQL даёт 23P01, соприкасающиеся интервалы допускаются; дополнительно проверены нулевая длительность (23514) и чужая организация исполнителя (23503).
- При ручном перечитывании обнаружено, что завершённую связанную задачу можно было бы вернуть в TODO после освобождения резерва. Заблокирована повторная активация любого освобождённого назначения, добавлен тест завершения заказа и попытки TODO. Редактирование действующей задачи также не может подменить orderId/assigneeId; отмена резерва выполняется в карточке заказа.
- Для профиля добавлено явное обновление после ошибки версии, блокировка закрытия на время сохранения. Кнопки команды сгруппированы с переносом для узкой ширины; точное радио/текстовое расположение карточек усилено относительно общих CSS labels. Проверяются мобильная страница команды и само переназначение на 390 px.
- Наладочные ошибки теста исправлены отдельно от бизнес-кода: accessible name кнопки заказа включает номер/клиента; snapshot устаревшего профиля должен явно выбирать проверяемого сотрудника, а не другого рекомендованного кандидата. Прогоны во время перезапуска watch API не считались успешной проверкой сценария; итоговые проверки выполнялись при готовом сервере.

## Границы, недоверенный ввод и конкуренция

- Только активный OWNER своей организации. Неавторизованный — 401, EMPLOYEE — 403, чужие заказ/сотрудник — 404. Профили OWNER не создаются. organizationId, готовые причины/eligible и прочие лишние поля отклоняются строгими схемами; Origin остаётся обязательным. В ответе профилей нет email, credential/session hashes, финансов или данных чужой компании.
- Нормализованные навыки, пределы длины/количества, уникальность, управляющие символы/одиночные суррогаты, дни 1–7, кратность 15 минут, диапазон смены и обязательный offset проверяются сервером. Текущий день/границы смены вычисляются через Intl Asia/Almaty. Проверены переход суток относительно UTC, полный интервал внутри смены, недостающий навык, нерабочий день, конец смены, дата в прошлом, закрытый заказ и срок раньше резерва.
- Причины допуска пересчитываются при подтверждении. Версии профиля/заказа и currentBookingId защищают старое предложение. Изменение графика не может сделать уже назначенные будущие/текущие работы несовместимыми. Ранжирование явно сортирует доступность, минуты, активные задачи, имя/UUID; требования к навыкам применяются целиком.
- Serializable + DB exclusion защищают разные одновременные заказы одного сотрудника. Partial UNIQUE защищает один текущий резерв заказа. Вставка в обход сервиса также проверена. Потеря ответа и параллельные повторы того же ключа создают одну задачу/уведомление/аудит. Ключ связан с автором, компанией, заказом и полным хешем запроса. Отмена по старому bookingId не отменяет новое назначение; параллельная отмена увеличивает версию только один раз.
- Переход заказа в COMPLETED/CANCELLED и освобождение/смена статуса задачи выполняются в той же транзакции. Ошибка аудита при переназначении оставляет прежний резерв и задачу целыми. Переназначение отнимает доступ прежнего сотрудника к фото при отсутствии других активных задач; новый получает доступ через текущую задачу. Уведомления и аудит сохраняются вместе с источником.
- Цена и платежи не меняются при назначении; сохранение точных 12345.67 проверено. Операции увеличивают версию заказа, поэтому прежнее подтверждение паспорта становится неактуальным согласно существующему правилу. История содержит выбранного сотрудника, интервал, требования, версию профиля, нагрузку и признак рекомендованного выбора, без исходной переписки клиента.

## Проверки и практические ограничения

Обязательные check:structure, typecheck, npm test и build выполняются перед коммитом. Backend unit — 23, локализация — 3. Интеграции scheduling/team/smart-orders — 26 тестов Node runner (включая 3 родительских теста). Microsoft Edge: новый полный сценарий профилей/рекомендации/потери ответа/переназначения/отмены/RU-KK-EN и 9 существующих workspace/onboarding — все 10 прошли. Снимки профилей, рекомендации и мобильного назначения просмотрены. Все тесты используют свои организации; после cleanup дополнительно совпали SHA-256 всех 23 прежних бизнес-таблиц с исходным снимком. Почта — local, затем возвращается конфигурация Gmail. Секреты, частные резервные копии, результаты тестов и сгенерированные Next-файлы не входят в коммит.

Модель назначает одного ответственного EMPLOYEE; график недельный, смена одинаковая для выбранных дней. Не учитываются дорога, перерывы, отпуска по отдельным датам, внешние календари, бригады и фактические опоздания. Обычная задача без времени не блокирует часы. Отсутствие кандидата требует решения владельца; альтернативное время не подбирается автоматически. Отключение сотрудника не освобождает его резервы автоматически. Лимит подбора — 200 сотрудников. Критерий объясним и детерминирован, оценка на реальном бизнесе и глобальная оптимальность не заявляются. Нужен доступный btree_gist; на установленном PostgreSQL 17 и в переносимых Windows-бинарниках расширение имеется. Старый переносимый кластер не переключался обратно и не мигрировался. Успешные тесты не являются гарантией безопасности или готовности к коммерческому запуску.
