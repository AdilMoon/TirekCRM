# Ревью согласования сметы, допработ и доставки

## Границы доступа и версия

- Владелец управляет только заказами своей компании. Роль повторно проверяется внутри выпуска и отзыва. HTTP проверяет сессию, роль, Origin, UUID и строгие контракты. Владелец чужой организации получает 404 при чтении и попытке отзыва, сотрудник получает 403.
- Предложение содержит случайный 256-битный токен во фрагменте URL. В таблице и поиске используется SHA-256. В истории владельца и аудите исходный токен отсутствует. Публичный ответ содержит разрешённые поля снимка, без клиента, телефона, почты, внутренних заметок или идентификатора компании. Открытие ссылки само по себе не согласует предложение. Для записи требуется явное согласие и номер версии. API отвечает с no-store, страница исключена из индексации и referrer.
- Статус предложения зависит от срока, отзыва и совпадения условий. Хеш охватывает клиента, название, итог и позиции, сохраняя повторяющиеся позиции. Оплата меняет версию заказа, сохраняя смысл сметы. Проверены неверная версия, изменение названия, подмена полей, отзыв и просрочка. После отзыва принятой ссылки сохраняются согласование и деньги.
- Два параллельных выпуска дают один выпуск. Частичный уникальный индекс ограничивает ожидающую версию. Второй индекс ограничивает принятую основную смету. Клиентский переход NEW → CONFIRMED и блокировка ручного перехода при ожидающей смете проверены тем же API. Уже согласованные условия защищены при ручном редактировании.

## Деньги и доставка

- Тиыны рассчитываются через BigInt. Допработы отсутствуют в заказе до согласования. Два конкурентных подтверждения сохранили одну отметку принятия, одну порцию новых позиций, одно изменение суммы и один набор уведомлений. Тест подтвердил 25 000,00 ₸ + 6 000,02 ₸ и остаток с учётом отдельной оплаты 100,00 ₸. Старая смета остаётся читаемым снимком на прежнюю сумму. Ошибка аудита откатывает изменение заказа, принятие и постановку в очередь.
- Запись уведомления связана с компанией, задачей, получателем и версией предложения. Среди связанных активных задач уведомление дедуплицируется по сотруднику. Для привязанных создаётся запись в очереди. Worker повторно проверяет активное назначение и привязку. При переназначении перед доставкой запись пропущена. Транспорт проверен с 429, повтором до SENT и последующим запуском без повторной отправки. Сообщение содержит номер и описания с количеством допработ. Цены и токен в сообщение не входят. Как и ранее, при потере ответа Telegram внешний текст может быть доставлен повторно.
- Доступ по ссылке отмечает действие её обладателя. Согласование по ссылке не устанавливает его личность. Владелец контролирует передачу ссылки и содержание видимых клиенту позиций. Внешнее открытие с телефона требует доступного HTTPS-адреса. Автоматическая отправка ссылки клиенту не входит в этот сценарий.

## Результаты

Пройдены check:structure, typecheck, 32 модульные проверки и production-сборка. Прошли 60 интеграционных проверок сметы, Telegram, уведомлений, расписания, паспорта и счетов, включая родительские тесты. В Microsoft Edge прошли три сценария. В их числе согласование обеих версий без сессии владельца, RU/KK/EN, ширина 390 px, точная сумма и отзыв ссылки. Проверен снимок мобильной страницы после правки формы.

Первый запуск в Edge выявил неоднозначный селектор открытия заказа и штатный HTTP 429 у существующей загрузки фото после интеграций. Селектор уточнён, сценарий фото прошёл после обновления окна ограничения. Лимиты не менялись. Изменения БД и тестовые действия изолированы по организациям. Доставка проверена через тестовый Telegram-транспорт. Миграция применена после локальной резервной копии БД с проверкой каталога. Секреты, архивы и тестовые артефакты не входят в коммит.
