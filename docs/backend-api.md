# Backend: поиск, версии и журнал
## Модули
- AuthModule — вход, выход и сессия; SessionGuard проверяет авторизацию и Origin.
- DatabaseModule — один провайдер Prisma и пул соединений.
- CrmModule — операции CRM, SearchService отвечает за поиск и выдачу страниц.
- AuditModule — запись событий внутри бизнес-транзакции и чтение истории.
- common/transaction.ts — Serializable с ограниченным повтором конфликтов и небольшой задержкой.

## Поиск
GET /api/clients/search?q=...&page=1&pageSize=20 — имя, компания, телефон, email.
GET /api/orders/search?q=...&status=IN_PROGRESS&page=1&pageSize=20 — название, номер, имя или компания клиента.

Ответ: { items, page, pageSize, total, pages }. page: 1–100000; pageSize: 1–100, по умолчанию 20; q: до 200 символов. Неизвестный статус и некорректные границы возвращают 400. Сортировка — createdAt DESC, id DESC, чтобы записи с одинаковым временем не перескакивали между страницами. Count и список читаются в одной RepeatableRead-транзакции. Между отдельными запросами страниц новые записи могут сдвигать offset; это не зафиксированный снимок всей выдачи.

Существующие GET /clients и GET /orders сохранены для обзорной панели и старых компактных списков; возвращают последние 200. Основные разделы клиентов/заказов и выбор клиента в заказе используют новый поиск. Формы оплаты, расходов и создания акта также используют поиск по всей базе заказов. Финансы и документы используют новые постраничные маршруты с фильтрами и итогами: см. financial-reports.md.

Поиск использует contains/ILIKE внутри организации. Это не полнотекстовый поисковик; нагрузочный профиль и необходимость trigram-индекса оценим на данных пилота. Замеры пропускной способности не выполнялись.

## Редактирование
GET /api/orders/:id возвращает свежую карточку и version.
PATCH /api/orders/:id принимает поля создания заказа и обязательный version.
- Разрешены NEW, CONFIRMED и IN_PROGRESS.
- COMPLETED и CANCELLED закрыты для правок.
- Сумма не может стать меньше полученных оплат за вычетом возвратов.
- После первой оплаты нельзя сменить клиента.
- Несовпадение version возвращает 409: UI сохраняет введённую форму и показывает предложение открыть заказ заново.
- Отсутствующий/чужой заказ возвращает 404.
- Оплата, смена статуса и редактирование увеличивают version.
- Повтор уже принятой оплаты с тем же ключом не меняет version и не добавляет событие.
- Удаление и пересоздание строк услуг, изменение заказа и запись аудита выполняются атомарно.
Версии защищают заказы, задачи и изменение доступа сотрудника; клиентские и организационные формы ещё не используют optimistic locking.

## История
GET /api/audit?page=1&pageSize=15&entityType=ORDER&entityId=<uuid>.
Разрешены фильтры entityType и entityId; организация всегда определяется из сессии. История доступна текущему владельцу компании; сотрудникам журнал недоступен.

Записываются создание/редактирование клиента и заказа, реквизиты компании, смена статуса, оплаты, расходы, создание акта. Запись содержит действие, автора, время и ограниченные данные операции. Пароли, токены, адреса, телефоны и свободные комментарии в историю не копируются. Имя автора и имя клиента/компании могут храниться для отображения.

Журнал начинается с новой миграции; старые события не выдумываются. Ошибка операции откатывает и её аудит. API изменения/удаления событий отсутствует. Это операционный журнал, а не криптографически защищённое хранилище: администратор БД сохраняет техническую возможность менять данные. Политика хранения и экспорт — следующие задачи.

## Проверки
npm run test:integration покрывает изоляцию компаний, стабильные страницы на 205 клиентах, email-поиск, запрет некорректных query, stale version, две конкурентные правки, гонку уменьшения суммы с оплатой, единственность аудита при повторе платежа и закрытые заказы.
Браузерный сценарий находит клиента вне прежних 200 записей, создаёт заказ, редактирует его, записывает оплату, проверяет отказ при уменьшении ниже оплаты и открывает историю.

Миграция 202610070002_order_version_audit добавляет version и AuditEvent с индексами. Данные существующих заказов и документов не сбрасываются.

## Безопасность аккаунта
AuthService отвечает за атомарную смену пароля, выпуск и отзыв сеансов; AuditWriterModule разделяет запись аудита и защищённый контроллер истории. Добавлены GET /auth/sessions, POST /auth/password, DELETE /auth/sessions/:id и POST /auth/sessions/revoke-others. Обе роли управляют только собственными входами. События ACCOUNT доступны владельцу в фильтре истории. [Контракты, миграция и ограничения](account-security.md).

## Создание компании
OnboardingModule предоставляет публичные GET /onboarding/status и POST /onboarding/register. Origin, строгая схема, уникальность email, атомарная запись компании/владельца/сеанса/аудита и лимит 5 запросов/мин защищают этот сценарий. В production он закрыт по умолчанию; подтверждение email ещё отсутствует. [API и ограничения](company-onboarding.md).

## Аннулирование черновиков

`POST /documents/:id/annul` (OWNER): `version`, `reason` (3–500 Unicode-символов, без управляющих кодов кроме перевода строки/табуляции и без одиночных суррогатов), `idempotencyKey`. Совпадающий повтор — прежний результат; конфликт — 409. `GET /documents/search` дополнительно принимает `status=DRAFT|ANNULLED`. Списки возвращают status/version; полное чтение — причину, автора и время. См. [документооборот](document-workflow.md).

## Обращения по персональным данным

OWNER: GET/POST `/api/privacy-requests`, GET/PATCH `/api/privacy-requests/:id`. Запись проверяет Origin, организацию, активного владельца и строгий контракт. Версии и ключи повторов защищают переходы; закрытие требует результата. Фильтры и подробный контракт — [privacy-requests.md](privacy-requests.md).
