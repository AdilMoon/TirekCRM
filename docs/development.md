# Tirek CRM

Рабочее название дипломного проекта: интеллектуальная система управления взаимоотношениями с клиентами и бизнес-процессами малого бизнеса Казахстана.

**Версия 0.1 — работающий локальный вертикальный срез.** Это не готовый публичный SaaS. Данные действительно сохраняются в PostgreSQL; демонстрационные организации и клиенты вымышлены.

## Что уже работает

- Вход владельца по email и паролю, серверные сессии и выход.
- Клиенты: создание и список с поиском по загруженным данным.
- Заказы: несколько услуг, количество, цена, срок, клиент и последовательные этапы выполнения.
- Частичные оплаты: точная арифметика, идемпотентность и защита от конкурентной переплаты.
- Расходы по категориям с необязательной привязкой к заказу.
- Сводка: поступления, расходы, чистый денежный поток, задолженность и стоимость выполненных работ.
- Акт для завершённого заказа: сохраняемый снимок данных, отдельная страница, печать / сохранение PDF средствами браузера.
- Адаптивный веб-интерфейс. Подсказки по срокам и статусам работают по явным правилам, без ИИ.

Денежный поток — поступления минус расходы. Он не называется прибылью. Стоимость выполненных заказов не равна полученным деньгам. Здесь нет банковской синхронизации, НДС или налогового учёта. Акт — **черновик**, без ЭЦП и без утверждения соответствия официальной форме.

## Стек и структура

- `backend` — NestJS 12, Fastify 5, Prisma 7, PostgreSQL.
- `frontend` — Next.js 16, React 19, TypeScript, собственные CSS-стили и Lucide.
- `packages/contracts` — общие типы, Zod-схемы входных данных, справочники статусов.
- `tests` — интеграционные проверки API и браузерные сценарии Playwright.
- `scripts` — настройка, локальный PostgreSQL, запуск и снимки интерфейса.

Точные версии зафиксированы в `package-lock.json`. Prisma выбран в стабильной линии 7, без перехода на RC 8. Tailwind/shadcn, BullMQ/Redis, S3, мобильное приложение и ИИ пока не подключены: они относятся к следующим этапам. API и UI первой версии полностью работают без этих сервисов.

## Запуск с нуля

Нужен Node.js 22.18+ и npm. Команды выполняются из корня репозитория.

```sh
npm ci
npm run setup
```

`setup` создаёт `.env` из примера, только если файла ещё нет, генерирует Prisma Client и собирает сервер. Затем в **отдельном терминале**:

```sh
npm run db:local
```

Это PostgreSQL 18 для разработки, установленный зависимостью npm. Системная служба не создаётся, сервер слушает только `127.0.0.1:54329`. Кластер хранится в `.local/postgres`; закрывайте его через Ctrl+C либо `node scripts/postgres.mjs --stop`. Не запускайте второй экземпляр с тем же каталогом. На Linux запускайте от обычного пользователя, не root.

В основном терминале:

```sh
npm run db:migrate
npm run db:seed
npm run dev
```

- Приложение: http://localhost:3000
- Проверка API: http://127.0.0.1:4000/api/health
- OpenAPI JSON (локальная разработка): http://127.0.0.1:4000/api/openapi.json
- Демо-вход: `owner@tirek.local`
- Пароль по умолчанию: `TirekDemo2026!` (настраивается через `DEMO_PASSWORD` **до** первого seed).

Seed не сбрасывает существующие данные. После первого создания смена `DEMO_PASSWORD` сама по себе не меняет уже сохранённый хеш. Production-запуск с `DEMO_SEED=true` запрещён кодом.

### Docker вместо переносимой базы

В репозитории есть `docker-compose.yml`. Задайте собственный `POSTGRES_PASSWORD`, запустите `docker compose up -d`, укажите тот же пароль в `DATABASE_URL`. Не запускайте Docker-БД и `db:local` одновременно на одном порту. Затем примените миграции и seed обычными командами.

### Текущий компьютер
Проект целиком размещён в D:\Projects\TirekCRM. Исходники, база .local/postgres, зависимости node_modules и кэш .npm-cache находятся на D:. Старую папку на C: удерживает открытая задача Codex; внутри оставлены только junction/symlink-ссылки на файлы и каталоги проекта на D:. Исходных копий и базы на C: нет. Резервная копия исходников до переноса находится в .local/migration-original на D:. Новые терминалы и IDE открывайте по пути на D:.

## Проверки

```sh
npm run check:structure
npm run typecheck
npm test
npm run build
```

При запущенных базе и API:

```sh
npm run test:integration
```

При запущенном веб-приложении:

```sh
npx playwright install chromium
npm run test:e2e
```

Либо используйте установленный Chrome, не скачивая отдельный браузер. В PowerShell:

```powershell
$env:PLAYWRIGHT_CHANNEL = 'chrome'
npm run test:e2e
```

Интеграционные и браузерные тесты создают отдельные организации и удаляют только собственные фикстуры. Проверяются разделение организаций, точность сумм, конкурирующие платежи, повторы, этапы заказа, неизменность снимка акта, выход из аккаунта, полный пользовательский путь и мобильная ширина. Это функциональные проверки, не нагрузочный бенчмарк.

## Архитектурные правила

1. Организация определяется по серверной сессии. `organizationId` не принимается из тела пользовательского запроса.
2. Связи клиент → заказ → оплата/расход/документ защищены составными внешними ключами с организацией.
3. Денежные значения передаются строками, вычисляются в целых тиынах (`bigint`) и сохраняются как `NUMERIC(18,2)`. Десятичные денежные строки форматируются точно через BigInt; числовые значения остаются только в визуализации графика.
4. Оплаты и расходы имеют уникальный ключ операции. Повтор с другим содержимым возвращает 409.
5. Запись оплат использует Serializable и ограниченные повторы конфликта транзакций. Переплата отклоняется.
6. Секрет сессии хранится в HttpOnly-cookie; БД содержит его SHA-256. Пароли хешируются scrypt со случайной солью. Мутации требуют допустимый Origin.
7. Роли OWNER и EMPLOYEE проверяются сервером. Сотрудник получает только свои задачи; владелец приглашает и отключает сотрудников. Матрица прав и ограничения — в team-and-tasks.md. Самостоятельной регистрации компании ещё нет.

Разделы клиентов и заказов используют серверный поиск и пагинацию. Обзорные и некоторые компактные списки ограничены 200; подробности в backend-api.md. Агрегаты сводки считаются по всей организации.

## Следующая итерация

1. Реквизиты, редактирование клиентов/открытых заказов и базовый журнал реализованы. Далее — расширение истории и управления доступами.
2. Приглашения, роли и задачи сотрудников; возвраты и корректировки финансов.
3. Счета и договоры, проверенные казахстанские формы, версии и статусы документов.
4. Очередь BullMQ/Redis для PDF, импортов и уведомлений; S3 для вложений.
5. Извлечение данных из обращения, оценка качества и подтверждение действий человеком.
6. React Native/Expo, пилот, мониторинг, резервные копии и нагрузочные испытания.

До реального размещения нужны отдельный процесс настройки организации, отключение демо-учёток, HTTPS, резервное копирование с проверкой восстановления, управление доступами сотрудников и проверка требований к данным/документам. Внешняя публикация и платные сервисы в этой итерации не настраивались.


Проверки команды и задач описаны в [team-and-tasks.md](team-and-tasks.md). Браузерный тест включает независимый сеанс сотрудника на ширине 390px и три языка. При ручном запуске тестов подряд учитывайте ограничение входа: 10 запросов в минуту с одного адреса. Не отключайте rate limit ради теста.

После реализации каждого запроса выполните отдельное адверсариальное ревью по AGENTS.md и сохраните конкретные результаты в docs/reviews/. Это просьба пользователя; обычный успешный прогон тестов не заменяет поиск способов нарушить предположения реализации.
