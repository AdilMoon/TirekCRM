# Финансовые операции и поиск документов

## Поведение интерфейса
Разделы «Финансы» и «Документы» используют серверную пагинацию и больше не обрезаются до последних 200 записей. Изменение фильтров возвращает на первую страницу. В финансах можно выбрать поступления/расходы, категорию, начальную и конечную дату, найти текст операции, текущий заказ или клиента. Ссылка номера заказа открывает его карточку.

Три финансовых итога — поступления, расходы и денежный поток — относятся ко всем записям, удовлетворяющим текущим фильтрам. Переключение страницы не меняет итогов. При загрузке или ошибке вместо денег показывается «—», а не фиктивные нули. Денежный поток не является бухгалтерской прибылью. Период относится к дате внесения записи (createdAt): отдельной даты совершения операции пока нет.

Поиск документов использует сохранённый снимок: имя/компанию клиента, название заказа, номер акта и номер заказа. Последующее переименование клиента или заказа не переписывает результаты поиска старого акта. Суммирование всех актов не предлагается: несколько черновиков по одному заказу не означают несколько продаж.

Общие формы оплаты, расхода и создания акта теперь ищут заказ во всей базе с пагинацией. Для акта предлагаются только завершённые заказы. В форме оплаты отменённые и полностью оплаченные заказы видны, но недоступны для выбора; окончательные проверки остатка выполняет API при записи. Существующий выбранный заказ сохраняется при изменении поискового текста.

## API и область доступа
Оба маршрута закрыты от EMPLOYEE и пользователей без сессии. organizationId берётся только из сессии; передача посторонних query-полей отклоняется.

GET /api/movements/search
- q: текст до 200 символов; нулевой символ запрещён.
- kind: INCOME или EXPENSE; category: ORDER_PAYMENT, MATERIALS, LABOR, TRANSPORT, RENT, OTHER.
- from / to: необязательные календарные даты YYYY-MM-DD, годы 0001–9999, начало не позже окончания.
- orderId: необязательный UUID.
- page: 1–100000; pageSize: 1–100 (по умолчанию 20).
- Ответ: {items,total,page,pageSize,pages,summary:{received,expenses,cashFlow}}. Все суммы — точные десятичные строки. summary учитывает те же фильтры, что список.
- В строке операции добавлен orderId; категория поступления имеет стабильный код ORDER_PAYMENT.
- Несовместимые kind/category естественно дают пустую выборку с нулевыми итогами.

GET /api/documents/search
- q, from, to, orderId, page, pageSize с теми же правилами.
- Ответ: {items,total,page,pageSize,pages}, строки содержат реквизиты из снимка.
- q с целыми цифрами также ищет номер акта или заказа; произвольный длинный номер не приводится к INT с переполнением.

Даты включают обе выбранные календарные даты в Asia/Almaty. PostgreSQL преобразует границы в UTC с учётом исторических правил часового пояса; верхняя граница — начало следующего дня, исключая его. Для 08.10.2026 интервал UTC: [07.10 19:00, 08.10 19:00). createdAt хранится как UTC timestamp without time zone, поэтому преобразование выполняется явно.

Список оплат/расходов формируется UNION ALL в БД, затем фильтруется, сортируется и ограничивается страницей. Порядок createdAt DESC, id DESC, kind DESC различает даже одинаковые UUID в двух таблицах. Count, суммы и страница читаются в одной RepeatableRead-транзакции. Документы сортируются createdAt DESC, id DESC.

Поиск использует буквальную подстроку без SQL wildcard-семантики: % и _ ищутся как символы. Все значения параметризованы через Prisma.sql. Миграция 202610080002_reporting_indexes добавляет составные индексы по организации, времени и id, не удаляя бизнес-данные. GET /dashboard теперь возвращает полный documentsCount.

## Совместимость и ограничения
Старые GET /movements и GET /documents остаются доступны владельцу и сохраняют ограничение 200 для совместимости. Рабочие экраны их не используют. GET /orders остаётся компактной выдачей обзора; формы выбора используют /orders/search.

Поиск подстроки и больших offset может быть дорогим на миллионах строк. Индексы не превращают поиск по свободному тексту/JSON в полнотекстовый: требуются замеры и план запросов на данных пилота. Между отдельными страницами новые записи могут сдвигать offset; это не зафиксированная выгрузка отчёта. Экспорт, корректировки, возвраты, банковская синхронизация и бухгалтерский учёт в этой итерации не добавлены.

API-суммы отображаются из десятичной строки через BigInt и formatToParts без преобразования суммы в Number. Числовые значения графика остаются приближёнными визуальными значениями, не используются для расчётов.

## Проверки
tests/reports.integration.mjs: 411 смешанных операций, 205 документов, одинаковые UUID в разных таблицах, точные суммы на всех страницах, фильтры, пустая выборка, границы дня и исторического пояса, сохранность поиска снимка, роли/организации, SQL-подобный ввод, нулевой символ, нулевой год, большие деньги.

tests/localization.test.mjs: точные дробные тиыны выше безопасного диапазона Number, минус для -0.01, отсутствие минуса у -0.00, RU/KK/EN.

Браузерный сценарий проверяет архивные записи, независимые от страницы итоги, неправильный период, оплату и акт по старому заказу, сохранение точной суммы, языки и ширину телефона.

С 14.10.2026 реестр объединяет ACT_DRAFT и INVOICE_DRAFT, поддерживает фильтр kind. Для счёта поле total в строке реестра означает сохранённый остаток к оплате; snapshot.total на странице документа остаётся полной стоимостью заказа. Подробности — [document-workflow.md](document-workflow.md).

## Дополнение 25.10.2026 — возвраты и сторнирования

Реализованы REFUND и EXPENSE_REVERSAL; категория возврата ORDER_REFUND. sourceId ссылается на исходную оплату/расход. Общие итоги учитывают их знак, период — дата корректировки; старые периоды не переписываются. Историческое ограничение об отсутствии возвратов/корректировок выше снято в этой части. Экспорт, банковская синхронизация и бухгалтерский учёт ещё не реализованы. [Сценарии, формулы и ограничения](finance-adjustments.md).
