# Безопасность аккаунта

Владелец открывает «Настройки → Безопасность аккаунта», сотрудник — одноимённую кнопку в своём рабочем пространстве. Интерфейс доступен на RU/KK/EN и на телефоне.

## Возможности и права

| Действие | OWNER | EMPLOYEE |
| --- | --- | --- |
| Список собственных активных сеансов | Да | Да |
| Смена собственного пароля с текущим паролем | Да | Да |
| Завершение своего выбранного/текущего сеанса | Да | Да |
| Завершение всех своих остальных сеансов | Да | Да |
| Управление чужими сеансами через эти маршруты | Нет | Нет |
| Журнал событий ACCOUNT своей организации | Да | Нет |

Отключение сотрудника владельцем остаётся отдельным сценарием команды и завершает все сеансы сотрудника.

## API

Все маршруты требуют действующий cookie. Мутации дополнительно требуют разрешённый Origin.

| Метод и путь /api | Тело | Ответ |
| --- | --- | --- |
| GET /auth/sessions | — | Массив id, createdAt, expiresAt, userAgent, current |
| POST /auth/password | currentPassword, newPassword | 201 {ok:true}, новый cookie |
| DELETE /auth/sessions/:id | — | 200 {current:boolean}; при текущем сеансе cookie удаляется |
| POST /auth/sessions/revoke-others | — | 201 {count:number} |

UUID id независим от секрета сеанса. В API не выдаются tokenHash, passwordHash или токен в JSON. Отсутствующий, чужой и истёкший сеанс для удаления возвращает 404; некорректный UUID — 400.

Пароль: 12–128 символов, отличается от текущего. Неверный текущий пароль — 403, нарушение схемы и лишние поля — 400. Сервер ограничивает смену пароля пятью запросами в минуту с одного IP, вход — десятью. Лимиты действуют в памяти одного процесса; за прокси и при нескольких экземплярах нужна отдельная конфигурация и общее хранилище лимитов.

## Атомарность и конкуренция

AuthService выполняет изменение пароля, удаление старых сеансов, выпуск нового и PASSWORD_CHANGED в одной Serializable-транзакции. Перед мутацией повторно проверяются текущий сеанс и активность пользователя. Конкурирующий запрос с уже отозванным сеансом не может использовать одну лишь ранее пройденную проверку SessionGuard.

Вход проверяет scrypt-хеш, затем повторно читает актуальный хеш и isActive внутри транзакции. Проверка защищает от входа со старым паролем, который начался до смены пароля, но дошёл до создания сеанса после неё. Сценарии проверяются на PostgreSQL, включая управляемую задержку перед транзакцией.

При новом входе удаляются истёкшие сеансы этого аккаунта и сохраняются до 20 последних активных, включая новый. Отзыв остальных сеансов не меняет пароль: владеющий паролем пользователь может войти заново.

События PASSWORD_CHANGED, SESSION_REVOKED, OTHER_SESSIONS_REVOKED не содержат секретов или User-Agent. У массового отзыва записывается только число удалённых сеансов.

## Миграция и интерфейс

Миграция 202610080003_account_security добавляет независимый UUID, дату создания, User-Agent и индекс. Для старых сеансов createdAt остаётся NULL, поэтому UI честно показывает неизвестное время создания. Бизнес-данные не сбрасываются. На новом размещении применяйте миграцию и новую сборку API согласованно: старый Prisma Client не заполняет новый обязательный UUID.

User-Agent ограничен 300 символами, управляющие символы удаляются; UI отображает его как текст, а не HTML. Он передаётся самим клиентом и не является доказательством личности или устройства. IP-адреса и геолокация не сохраняются.

После изменения данных старые ответы загрузки списка игнорируются по номеру запроса. Ошибка отзыва остаётся в диалоге с возможностью повторить действие. Добровольный выход не сопровождается ложным сообщением об истечении сеанса.

## Ограничения

- Нет восстановления забытого пароля, подтверждения email, MFA и оповещения о новом входе. Это следующие задачи перед пилотом.
- Cookie используется совместно вкладками одного браузера; это один сеанс, а не отдельный на каждую вкладку.
- После потери ответа успешной смены пароля браузер может не получить новый cookie. Нужно войти с новым паролем; операция не повторяется автоматически.
- Отзыв прекращает последующие запросы. Уже показанную информацию невозможно забрать обратно; это не механизм отмены ранее начатых бизнес-операций.
- HTTPS, Secure-cookie в production, общее хранилище лимитов, настройки прокси и резервные копии должны проверяться на целевом размещении. Нагрузочные испытания не выполнялись.
