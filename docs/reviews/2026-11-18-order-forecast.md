# Прогноз прибыльности заказа

Прогноз читается вместе с планом и фактом из одного снимка PostgreSQL. Ставки и часы выбираются по заказу и организации. Используется существующая проверка сессии и роли владельца. Проверки через API подтвердили ответы 401 без сессии, 403 для сотрудника и 404 для владельца другой организации.

Для активного заказа оставшаяся работа оценивается по исходной плановой длительности за вычетом подтверждённых и поданных часов, минимум ноль. Если исполнителям потребуется больше времени, чем заложено в плане, перерасход проявится после подачи часов или изменения плана. Будущие часы оцениваются по общей фактической ставке, а при её отсутствии по плановой. Для поданных часов в первую очередь используется индивидуальная ставка. Стоимость труда округляется один раз после суммирования всех минут. Пустые входные данные оставляют зависимые показатели неопределёнными. Явный ноль учитывается как сумма.

Остаток бюджета прямых расходов считается после вычета проведённых затрат с учётом сторно. Прогноз предполагает полное использование остатка. Фактически понесённые сверх бюджета расходы сохраняются. Для завершённых и отменённых заказов исключаются будущие часы и остаток бюджета, а уже поданные часы остаются в оценке до решения по табелю. Отмена обнуляет выручку. При нулевой выручке маржа неопределена.

На изолированном стенде заказ с выручкой 1 000 ₸, четырьмя плановыми часами, двумя подтверждёнными и одним поданным часом дал прогноз труда 900,04 ₸ и расходов 300 ₸. После подтверждения поданного часа фактическая стоимость труда выросла с 500,02 ₸ до 700,03 ₸. Прогноз убытка 200,04 ₸ сохранился. Также проверены закрытие при наличии поданных часов, отмена, отсутствие плана, нулевая ставка, сторно и перенос расхода между заказами.

Прошли сборка Docker, проверка структуры и переводов, 29 модульных тестов API, три проверки локализации и интеграционный набор прибыльности. В Microsoft Edge пройден сценарий от подачи времени сотрудником до просмотра прогноза владельцем на ширине 390 px с проверкой значений трёх столбцов маржи и отсутствия горизонтального переполнения таблицы. Интеграционный и браузерный тесты использовали отдельную базу.
