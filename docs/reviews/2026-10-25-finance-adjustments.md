# Адверсариальное ревью: возвраты и исправления финансов

Дата: 25.10.2026. Область: FinanceModule, миграция PaymentRefund/ExpenseReversal, чистая оплата заказа, счета, отчёты/обзор, формы и RU/KK/EN. После реализации отдельно перечитаны сервисы, SQL, контракты, изменённые потребители сумм и интерфейс. Независимый внешний аудит не проводился.

## Риски и результаты проверки

| Попытка нарушить правило | Результат |
| --- | --- |
| Чужой платёж/расход, сотрудник, отсутствие сеанса | Чужой id — 404; EMPLOYEE — 403; отсутствие сеанса — 401, для чтения и записи |
| Подделка Origin, организации, автора, даты, суммы сторнирования | Отказ 403/400; организация из сеанса, активный OWNER повторно читается в транзакции; сумма сторнирования берётся из расхода |
| Отрицательная/нулевая сумма, экспонента, 3 знака после точки, длинный ввод, NUL/суррогат | Отклонены строгими контрактами; причины не исполняются как HTML |
| Три одновременных запроса одного возврата | Одна запись, один id, один аудит и одно увеличение версии заказа |
| Два разных возврата по 60 при остатке 90.15 | Один 201, один 409; остаток 30.15, чистая оплата и долг точны |
| Старый ключ после следующих возвратов / регистр UUID / 10.1 против 10.10 | Повтор возвращает ту же сохранённую запись, денег повторно не списывает; несовпадающий ввод — 409 |
| Возврат одновременно с новой оплатой / отменой заказа | Сохранён допустимый чистый остаток; переплата не проходит. Отмена при оставшейся оплате отклоняется; после полного возврата разрешена существующими переходами |
| Новая оплата после возврата | Доступен восстановленный остаток; превышение на один тиын — 409. Отменённый заказ не принимает новые оплаты |
| Два сторнирования разными ключами | Ровно один успех; второе — 409. Повтор успешного ключа не создаёт вторую компенсацию. Новый правильный расход учитывается отдельно |
| Сбой аудита | Возврат/сторнирование и версия заказа откатываются полностью |
| Старый actor после деактивации / составная связь другой компании | Запись от старого actor запрещена; прямые межорганизационные связи отклонены FK |
| Исходные записи и документы | Payment и Expense равны исходным объектам после корректировки; старый снимок счёта неизменен; новый счёт учитывает чистую оплату, устаревшая версия получает 409 |
| Денежная точность за пределом безопасного Number | Для 90071992547409.99 возврат 0.01 даёт 90071992547409.98, долг 0.01; отчёт, обзор и карточка совпадают; полное сторнирование большого расхода точно компенсирует сумму |
| Переписывание прошлых периодов | Оплата/расход 2020 года сохраняются в старом периоде; корректировки появляются по собственной дате, месяц может иметь отрицательные итоги |
| SQL-подобный текст / общие итоги | Параметризованные значения и буквальный поиск; % не становится wildcard. Один общий SQL-источник для финансов, обзора и совместимого /movements; итоги обзора читаются в одном RepeatableRead-снимке |
| Потерянный ответ, затем 429 | В браузере возврат сначала принимается сервером, ответ теряется, следующий запрос получает 429; последующий повтор использует то же тело/ключ. Одна запись и неизменная исходная сумма. Отдельно проверен потерянный ответ сторнирования |
| Устаревший остаток и потеря роли в открытой форме | Сервер отклоняет лишний возврат. После открытия заново виден полный возврат. Отзыв роли перед сторнированием даёт 403, данные карточки скрываются, записи нет |

## Выявленные дефекты и исправления

1. Старый MoneyChart принудительно использовал `Math.max(1, value / scale * 100)`. Воспроизведение для −0.01 даёт положительную высоту 1, что скрывало бы отрицательный итог после возврата старой оплаты. Для месяцев с отрицательными суммами добавлена таблица. Браузерная регрессия проверяет видимые −0.01 и −10.11 и отсутствие горизонтального переполнения на 320 px.
2. Новая текстовая форма суммы первоначально отправляла десятичную запятую без преобразования. Воспроизведено `refundSchema.safeParse({amount:'10,10', ...})`: false. Поле теперь преобразует запятую в точку без вычислений Number; браузерный сценарий вводит `10,10`, повторяет запрос после сбоя/429 и проверяет одну корректировку. Формат API остаётся строгим.
3. Пересмотрены все потребители оплаченной суммы: сериализация/редактирование/отмена/оплата заказа, новый счёт, outstanding и месяцы. Отменённый заказ не должен показывать долг после полного возврата — в DTO долг обнулён, регрессия проверяет карточку и обзор.

## Ограничения

Нет банковских переводов/сверки, уменьшения цены завершённой услуги, исправления уже зарегистрированного возврата, атомарной замены расхода, экспорта и бухгалтерских проводок. Сторнирование — только полное и один раз; правильный расход вносится отдельно. Исходные даты не меняются, отдельной даты фактического денежного движения пока нет.

Ключ UI живёт в открытой форме; после её закрытия при неопределённом результате необходимо проверить историю. Разные ключи разных действий не распознают один реальный банковский возврат автоматически. При прямом доступе администратора БД серверные правила можно обойти; производственные права, восстановление и журналирование инфраструктуры ещё требуют проверки. Карточка оплаты загружает всю историю возвратов без пагинации, производительность больших объёмов не измерена. Реальные телефоны и экранные клавиатуры не тестировались; мобильный сценарий выполнен в эмуляции Edge.

Успешные тесты не являются гарантией безопасности или готовности к коммерческому запуску. Условия [внешнего пилота](../pilot-readiness-kz.md) остаются в силе.
