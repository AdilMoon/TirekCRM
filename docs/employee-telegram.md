# Telegram для сотрудников TirekCRM

## Чеки расходов по заказу

1. Сотрудник получает чек у продавца после покупки за счёт компании или покупки, которую компания возместит. В личном чате бота открывает `/tasks`, выбирает свою активную задачу и нажимает **Чек расхода**. В ответе бот показывает номер заказа.
2. В течение 15 минут сотрудник отправляет фото бумажного чека или снимок экрана с электронным чеком как обычное изображение. В первой строке подписи указывает сумму в тенге, например `1 250,50`. Во второй строке можно написать назначение покупки. Для следующего чека нужно снова выбрать действие в карточке задачи.
3. Владелец открывает **Финансы → Чеки сотрудников** или **Заказы → карточка заказа → Прибыльность**. Сверяет сумму и покупку по фото, выбирает категорию и подтверждает расход. Фото можно открыть в полном размере. Ошибочный чек можно отклонить, после чего сотрудник сможет прислать исправленную заявку.
4. Подтверждение создаёт расход по этому заказу и обновляет его фактическую себестоимость. Список хранит решения по статусам. Повторное подтверждение одной заявки создаёт одну проводку. Повтор того же изображения по одному заказу распознаётся до отклонения. Для разных снимков одного бумажного чека дубли проверяет владелец.

Клиентская оплата регистрируется отдельно как поступление. Если клиент сам оплатил материалы и компания ему ничего не возмещает, проводить такую покупку как расход компании не требуется. Чек из магазина выдаёт продавец. TirekCRM сохраняет подтверждение покупки для внутреннего учёта. Фото доступно владельцу организации и не публикуется в клиентском паспорте.


## Локальная настройка

Бот создан пользователем через @BotFather: `@tirekcrmbot`. В частном корневом `.env` настроены `TELEGRAM_DELIVERY=telegram` и `TELEGRAM_BOT_TOKEN`. Токен не помещают в чат, Git, снимки экрана или команды с открытым URL. В `.env.example` интеграция выключена; другой компьютер требует своего локального секрета.

`npm run dev:https` запускает API вместе с Telegram worker. Worker использует [getUpdates / long polling](https://core.telegram.org/bots/api#getupdates): достаточно исходящего HTTPS к api.telegram.org, публичный адрес localhost и входящий webhook для этого не нужны. Компьютер, PostgreSQL и приложение должны работать, интернет должен быть доступен. Лишь один потребитель обновлений должен использовать этот токен; экземпляры одной БД дополнительно координируются lease-записью. Существующий webhook другой интеграции автоматически не удаляется.

## Как сотруднику подключиться

1. Войти в CRM под **аккаунтом сотрудника**. Владелец видит состояние бота в настройках, но свою учётную запись к рабочим задачам бота в этой версии не подключает.
2. Нажать «Настроить Telegram» → «Создать ссылку подключения» → «Открыть бота и нажать Start».
3. В личном чате бота нажать Start. Бот попросит вернуться в CRM.
4. В CRM обновить состояние, проверить имя и @username своего Telegram-профиля, отметить согласие и подтвердить подключение. До этого бот не получает доступ к задачам аккаунта. Если показан чужой профиль, создать новую ссылку и не подтверждать его.
5. В боте отправить `/tasks`. Новые назначения после привязки приходят автоматически через очередь. Уже существующие активные задачи доступны через `/tasks`, без массовой рассылки старых уведомлений.

Личная ссылка действует 10 минут. Новая отключает предыдущую, потерянный ответ создания ссылки требует её перевыпуска. На сервере хранится только SHA-256 токена. Каждому Telegram-пользователю допускается одна текущая привязка к данному боту; для другого аккаунта CRM сначала отключают прежнюю. В режиме localhost вход и подтверждение в CRM выполняют на этом компьютере; бот после привязки доступен с телефона через Telegram. Для самой CRM с телефона понадобится размещённый HTTPS-домен.

## Задачи и фото

- `/tasks` показывает по пять активных TODO/IN_PROGRESS задач с переходами по страницам. Кнопка задачи открывает название, описание, срок или точный интервал работы по Алматы.
- «Начать работу» переводит TODO в IN_PROGRESS; затем появляется «Завершить задачу» для перехода в DONE. Изменение сразу видно в CRM, владельцу создаётся уведомление, в аудите указан источник TELEGRAM. Завершение задачи не завершает заказ и не освобождает его рабочий интервал: это отдельное действие владельца в заказе.
- Кнопка содержит версию задачи. Повтор сразу после успешного действия не меняет версию и не создаёт ещё одно уведомление; устаревшая кнопка после другого изменения предлагает открыть карточку через `/tasks`. Через старую кнопку нельзя вернуть завершённую задачу в работу.
- В задаче, связанной с заказом, есть кнопка «Фото результата». После неё бот принимает обычные фото в течение 15 минут. Сначала дождитесь приглашения бота отправить снимок; старое фото, отправленное до выбора задачи/привязки, не переносится в новый контекст.
- Фото отправляют **до завершения задачи**. Для завершённой/отменённой задачи бот объясняет причину отказа. Старая карточка своей задачи показывает её текущий статус без кнопок изменения и загрузки; чужие карточки недоступны. Если прежняя тестовая задача уже завершена, выберите новую активную через `/tasks`.
- Фото сохраняется в существующий паспорт заказа: этап AFTER, публикация клиенту выключена. Владелец проверяет снимки в CRM и решает, какие можно опубликовать. Текст подписи к фото не управляет публикацией или заказом.
- `/cancel` отменяет выбор задачи для фото. `/stop` отключает привязку, в том числе когда аккаунт CRM деактивирован. В CRM есть «Отключить Telegram».

Фото принимаются именно как изображение Telegram, не как документ/файл. Вход до 5 МБ и 12 млн пикселей, JPEG/PNG/WebP без анимации; сервер проверяет сигнатуру, уменьшает и перекодирует изображение без EXIF. Затем применяются прежние ограничения паспорта: до 6 снимков на заказ, итоговый JPEG до 200 КБ. Повтор одного Telegram message_id не создаёт второе фото; повторная отправка пользователем как нового сообщения является отдельным снимком. Любое добавление фото увеличивает версию заказа и делает прежнее подтверждение результата неактуальным.

## Доступ и доставка

Привязка использует числовой Telegram user ID из доверенного ответа Bot API и подтверждение текущего пользователя CRM. @username служит только отображением. Группы, каналы, несовпадающие sender/chat ID и сообщения ботов игнорируются. Веб-API не принимает от браузера Telegram user ID, организацию или готовые Telegram updates.

Список и уведомления показывают только активные задачи текущего исполнителя; собственная закрытая задача доступна по старой кнопке только для чтения. Перед отправкой карточки проверяются пользователь, организация и текущий исполнитель. На записи статуса в сериализуемой транзакции повторно проверяются активность аккаунта, роль, организация, UUID привязки, bot/user ID, исполнитель, версия и допустимый переход. На записи фото проверяются активность задачи, UUID текущей привязки и выбранная задача; отвязка или переназначение во время скачивания не разрешает сохранить снимок. Финансовые поля, контакты клиента, внутренние заметки заказа, документы и приватные фото других задач в карточку не входят. Названия/описания задач и отправленные фото проходят через Telegram: сотрудник видит это при подтверждении.

Назначение задачи, уведомление внутри CRM и запись очереди Telegram сохраняются атомарно. Очередь хранит ссылки на события, не текстовые копии; карточка формируется из актуальных данных. Устаревшая задача пропускается. Есть повторы при временных ошибках, backoff и учёт retry_after. После шести неудачных попыток доставка помечается FAILED; она не создаёт ещё одну бизнес-задачу. Блокировка бота (403) снимает привязку. Доставка текста имеет семантику «как минимум один раз»: при потере ответа Telegram возможно повторное уведомление. Полученное человеком сообщение невозможно отозвать проверкой доступа в CRM; проверки блокируют новые чтения и действия, а не сохранённые копии.

Offset хранится по bot ID, обработанные update_id — 30 дней. После длительного простоя обновления запрашиваются без прежнего offset, с дедупликацией. Telegram хранит ожидающие updates ограниченное время (см. [Bot API](https://core.telegram.org/bots/api#getting-updates)); работа выключенного компьютера не гарантируется, задачи остаются в CRM и `/tasks`. Необрабатываемый постоянный ответ 400 не блокирует остальные updates. Секреты, полные provider errors, сообщения и изображения не записываются в серверный журнал.

## Проверки

```powershell
npm run check:structure
npm run typecheck
npm test
npm run build
# Тестовый сервер запускается с временными переменными; .env с реальным ботом не меняют.
$env:TELEGRAM_DELIVERY='disabled'
$env:MAIL_DELIVERY='local'
$env:PASSWORD_RESET_DELIVERY='local'
npm run dev:https
# В другом терминале, при работающем API
$env:WEB_ORIGIN='https://localhost:8443'
node --test tests/telegram.integration.mjs
# Edge
$env:NODE_EXTRA_CA_CERTS=(Resolve-Path '.local/caddy/pki/authorities/local/root.crt').Path
$env:TEST_WEB_URL='https://localhost:8443'
$env:PLAYWRIGHT_CHANNEL='msedge'
npx playwright test tests/browser/telegram.spec.ts
```

В интеграционных проверках Bot API заменён явным fake transport, база/транзакции/права/фотографии реальные и принадлежат только тестовым организациям. В UI-тесте Telegram-провайдер и этап предъявления профиля моделируются перехватом API-запросов; серверная безопасность проверяется отдельным набором. После проверок новый обычный терминал без временных overrides возвращает конфигурацию `.env`. Отдельная живая проверка подключает реальный getMe/getUpdates; сквозная отправка из физического Telegram сотрудника требует его входа и подтверждения своей привязки.
